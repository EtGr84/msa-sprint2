# Выявленные проблемы

Решении as-is содержит проблемы, присущие монолиту.

- В текущей архитектуре одна общая база данных без изоляции доменов.
- Сильная связанность между модулями монолита, - падение одного модуля может привести к падению всей системы.
- Отсутсвие возможности выделения дополнительных ресурсов тем модулям, в которых необходимы дополнительыне ресурсы.
- Отсутсвие переменных для отражения констант. Вместо этого константы указаны числами в коде.

# Предлагаемое решение

Предлагается перейти на микросервисную архитектуру с использованием паттерна Strangle Fig. Первым модулем для перехода на MSA предлагается выбрать UserService.

№ Предлагаемые архитектурные подходы:

- каждый сервис владеет своей бд
- единая точка входа (api gataway)
- Kafka как очередь событий

# Последоватльеность действий для выноса сервиса UserService, а также каждого последующего.

|**№ Шага**|**Описание шага**|
| :-: | :- |
| 01 | Развертываем мигрируемый сервис. Сервис должен содержать собственную БД. |
| 02 | Мигрируем данные в новую БД |
| 03 | Тестируем новый сервис |
| 04 | Переключаем GateWay на новый серсис |
| 05 | Отключаем модуль в монолитном решении |

# Критерии по которым был выбран UserService

ReviewService - не зависит от других сервисов, имеет 1 потребителя, полная изоляция данных.
HotelService  - не зависит от других сервисов, имеет 1 потребителя, полная изоляция данных.
UserService - не зависит от других сервисов, имеет 2 потребителя, полная изоляция данных.
PromoService  зависит от других сервисов, имеет 1 потребителя, полная изоляция данных.

Как видно из таблицы, у нас 3 сервиса, не зависящих друг от друга, с полной изоляцией данных. Среди них предлагается выбрать UserService, т.к. он 
может стать фундаментом для переноса на MSA всех остальных сервисов.
